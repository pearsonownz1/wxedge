Keys stored, backoff in, trader found dead and resurrected. Approve on all of it, with one architecture concern before you deploy, and it's a real one:

Spawning the trader as a child of the API server collides with Autoscale. Your deployment is Autoscale, "3 Max" instances — which means Replit can run multiple copies of the API server under load, and scale to zero when idle. Child-process trader inherits both problems: under load you get two or three traders running simultaneously (each polling, each generating signals, each trying to create proposals), and when traffic dies overnight the instance — trader included — can be reaped, which resurrects the collector-gap problem wearing a new hat. The DB constraints we built will absorb some of the blast (the partial unique index means duplicate proposals get rejected, the CAS on approve means no double orders), but you'd still get tripled Kalshi polling (hello again, 429s), racing risk-officer reads, and confusing duplicate-rejection noise in the logs.

Two acceptable fixes, in order of preference:

Leader election via Postgres advisory lock — cheap and robust: on startup, each would-be trader tries pg_try_advisory_lock(SOME_CONSTANT); the one that gets it runs, the others log "standby: another trader holds the lock" and idle, retrying every minute. One trader guaranteed across any number of instances, automatic failover if the leader's instance dies, ~15 lines. Do this regardless of anything else.
And/or pin the deployment to exactly 1 instance (max=1), which your traffic — you and the grant committee — will never notice. That also settles the scale-to-zero question if the plan includes keeping one instance warm; check whether Replit's Autoscale ever idles a min-1 config, because the overnight snapshot record depends on it. (The long-term clean answer is still the trader on a Reserved VM/always-on process, but lock + pin is fine for demo timeline.)

The overnight test tells you the truth either way: after deploying, tomorrow's snapshots table should show unbroken ≤5-minute deltas and exactly one Production trader process spawned line without restarts. Gaps or multiple spawn lines = the architecture question answering itself.
