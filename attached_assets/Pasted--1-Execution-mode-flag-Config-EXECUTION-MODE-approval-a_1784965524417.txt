
## 1. Execution mode flag

Config: `EXECUTION_MODE = "approval" | "auto" | "shadow"` (default `approval`).

- `approval`: signals that pass risk checks become *proposals* awaiting human decision. Executor fires only on Approve.
- `auto`: current Phase A behavior (kept for comparison slides; leave gated).
- `shadow`: unchanged.

Mode is logged at startup and stamped on every order row.

## 2. Data model (one new table, one new status)

```sql
CREATE TABLE approvals (
  id            serial PRIMARY KEY,
  signal_id     int NOT NULL REFERENCES signals(id) UNIQUE,
  ticker        text NOT NULL,               -- denormalized for the partial index
  side          text NOT NULL,               -- 'YES' | 'NO'
  proposed_ts   timestamptz NOT NULL,
  expires_ts    timestamptz NOT NULL,        -- proposed_ts + 30 min
  card_json     jsonb,                       -- template trade card; GPT enrichment is async/deferred
  decision      text CHECK (decision IN ('approved','denied','expired')) ,
  decision_ts   timestamptz,
  latency_ms    bigint,                      -- decision_ts - proposed_ts, in ms (histogram-friendly)
  recheck_ok    boolean,                     -- approve-time revalidation result
  recheck_note  text                         -- why revalidation failed, if it did
);
```

**Additional constraints (per dev review):**
- The business rule "one open proposal per ticker+side" is enforced in the DB, not just the risk officer:
  `CREATE UNIQUE INDEX one_open_proposal ON approvals (ticker, side) WHERE decision IS NULL;`
  (denormalize `ticker` and `side` onto the approvals row for this). The `signal_id UNIQUE` constraint stays — it's a different invariant (one proposal per signal).
- `signals` has **no status column today** — adding `status` (with `pending_approval`) is an explicit schema migration, step 1 of the build order, not incidental.

Orders placed via approval store `approvals.id` on the order row.

## 3. Proposal lifecycle

```
signal passes risk officer
        │  EXECUTION_MODE=approval
        ▼
create approvals row (pending) ──▶ render card v1 (template, synchronous, no LLM call)
        ▼
shows in /approvals queue ── waits ──▶ expires_ts passes ⇒ decision='expired'
        (expiry sweep OWNER: the trader loop, at each 4-min tick, alongside the
         settlement audit job — marks expired rows and logs the sweep count.
         Also run the sweep once at trader startup to clear anything that
         expired while the process was down.)
        ▼
human taps Approve ──▶ REVALIDATE (§4) ──ok──▶ executor places post-only limit order
        │                                └─fail─▶ decision recorded, UI shows updated picture
human taps Deny ──▶ decision='denied', logged, done
```

Rules:
- One open proposal per ticker+side at a time (reuse duplicate_guard).
- Proposals do NOT queue orders; nothing touches Kalshi until Approve passes revalidation.
- **Card v1 is a pure template** rendered from the signal struct (headline, model % vs market %, edge, max loss, running high, hours to peak) — no LLM call, no latency, no new failure mode on the demo path. The GPT card from the LLM-layer spec becomes an **async enrichment/backfill** that upgrades the card text after the fact (and for the presentation export); if it never runs, the template stands. This keeps "AI explains" in the story without putting OpenAI availability between the human and the Approve button.

## 4. Approve-time revalidation (P0)

On Approve, before placing the order, re-run against the **latest** snapshot:
1. Freshness: book + observation age ≤ `max_age_min`.
2. Bracket still alive (not eliminated by running high).
3. Edge still ≥ `cancel_edge` at the *current* executable price (not the proposal-time price).
4. Risk officer full re-check (exposure may have changed since proposal).

All pass ⇒ place order at current price or better; store `recheck_ok=true`.
Any fail ⇒ no order; store `recheck_ok=false` + `recheck_note`; UI shows: "This proposal expired — here's what changed," with the stale vs. current numbers side by side. (This UI moment is presentation gold; make it look intentional, not like an error.)

## 4a. API contract (single mutation endpoint)

All decision logic is server-side; the UI is dumb buttons against one endpoint.

`PATCH /api/approvals/:id` with body `{ "action": "approve" | "deny" }`

Responses (all 200 unless noted):
- Deny → `{ "result": "denied" }`
- Approve, revalidation passes, order placed →
  `{ "result": "order_placed", "order": { "id", "ticker", "side", "limit_price_cents", "contracts", "status" } }`
- Approve, revalidation fails →
  `{ "result": "stale", "recheck_note": "...", "diff": { "field": { "at_proposal": x, "now": y }, ... } }`
  (the `diff` object drives the "here's what changed" view — include at minimum price, edge_net, running_high, and any freshness/eliminated flags that failed)
- Already decided/expired → `409 { "result": "conflict", "decision": "expired" }`
- Unknown id → `404`

Idempotency: a repeated approve on an already-approved row returns the existing order (no double placement). Concurrency: decision update uses `WHERE decision IS NULL` compare-and-set so two simultaneous clicks can't both proceed; the loser gets the 409.

## 5. UI — Approval Queue

New page `/approvals` in the existing app. **Desktop-only for v1** — mobile layout and notifications are explicitly deferred (P2); the demo runs in a browser tab that's already open during trading hours.

Each pending proposal renders as a card:
- **Headline** from trade card ("Buy YES on NYC 91-92° at 27¢ — model sees 34%")
- Model % vs market %, edge in pts, **max loss in cents** (bold — this is the number the grant cares about)
- Running high + hours to expected peak (the "why now")
- Countdown to expiry
- Two buttons: **Approve** / **Deny**. Approve requires one confirm tap ("Place order: 1 contract, max loss 27¢?").

Below the queue: decision history (decided proposals with outcome once settled — proposal → decision → result on one line).

No notification system in v1 (deferred with mobile). The queue page auto-refreshes on the poll interval so an open tab is sufficient.

## 6. Logging & grant reporting

- Every proposal, decision, latency, and revalidation result is queryable from `approvals`.
- `GET /api/approvals/report?from=&to=` returns: proposals made, approved/denied/expired counts, median decision latency, orders placed, P&L of approved trades, and (nice stat) hypothetical P&L of *denied* trades once settled — "what the human's judgment added" is a headline slide.

**Denied-trade counterfactual — methodology (design this join up front, per dev review):**
- Join: `approvals (denied) → signals (ticker, side, limit_price, station, settlement_date) → settlements (station, date) → settled bracket`.
- Outcome rule: proposal's bracket contains the settled value ⇒ counterfactual win (100¢ − limit_price per contract, minus the same fee model as real orders); else loss of limit_price.
- **Fill assumption is the honest caveat:** assume the order would have filled at the proposal-time limit price *only if* `book_at_decision` showed ask ≤ limit at proposal time; otherwise mark the counterfactual `fill_uncertain=true` and report those separately. Never blend certain and uncertain counterfactuals into one number.
- Label the stat in the report and any slide as *"estimated, assumes fill"* — it is an upper-bound-flavored estimate, not realized P&L, and presenting it as such is what makes it credible.
- Store nothing; compute at query time from the three tables. If the join gets slow later, materialize then.
- Stamp `EXECUTION_MODE` and `approvals.id` on orders so the audit trail reads: signal → risk check → human approval → order → settlement, with timestamps end to end.

## 7. What does NOT change

- Risk officer limits still bind (a human Approve cannot exceed caps — if it would, the proposal is never shown).
- Kill switch still cancels resting orders and freezes new proposals.
- Deterministic alerts unchanged.
- LLM remains explanation-only: the trade card describes the proposal; it does not score, rank, or recommend beyond the mechanical confidence_label already specced.

## 8. Acceptance checklist

- [ ] In approval mode, zero orders reach Kalshi without an `approvals` row with decision='approved' and recheck_ok=true
- [ ] Expired proposals auto-mark and disappear from the queue
- [ ] Approve on a gone-stale proposal places NO order and shows the changed-picture view
- [ ] Deny is one tap, logged with latency
- [ ] Duplicate proposal for same ticker+side while one is pending is suppressed
- [ ] Kill switch clears the pending queue
- [ ] Report endpoint returns correct counts against a seeded test dataset
- [ ] Partial unique index rejects a second open proposal for the same ticker+side; allows one after the first is decided
- [ ] Startup sweep expires proposals that lapsed while the trader was down
- [ ] Card renders instantly from template with LLM enrichment disabled entirely
- [ ] Double-click / repeated approve places exactly one order (idempotent, CAS-guarded)
- [ ] Approve and deny racing on the same proposal: exactly one wins, the other gets 409
